# Realistic CPU-cluster physical sample

## Problem
The previous physical sample (`SUB_A/B/C.json` + notched TOP) was unrealistic:
`generate_physical.py` placed dense grids with `pitch=1` while cells are `1x2`/
`2x1`, so adjacent cells overlapped and density bins exceeded 1.0; the TOP only
filled a tiny `100x50` patch, leaving ~95% of the die empty.

## Goal
Replace it with a realistic CPU-cluster floorplan that satisfies:
- TOP `CPU_CLUSTER` with 4 cores in the 4 corners using 4 orientations (N/W/S/E)
- each core contains `IFU` / `IEX` / `LSU` sub-blocks (separate block files)
- each sub-block has thousands of standard cells + a small SRAM bank
- an uncore region: interconnect logic in the central cross + 8 L2 SRAM macros
- ~100k instances, average density ~60%, varied local density, max bin <= 1.0

## Data design
Files (all generated by `sample_data/physical/generate_physical.py`):
- `cell_info.json` — 13 std cells (height 1.0) + SRAM 40x32 macro
- `instance_info.json` — TOP `CPU_CLUSTER`, square die
- `CORE.json`, `IFU.json`, `IEX.json`, `LSU.json` — nested blocks

Hierarchy: `CPU_CLUSTER` -> `CORE` (4x, rotated) -> `IFU`/`IEX`/`LSU` -> leaves.
Sub-blocks are defined once and instantiated 4x through the shared `CORE`
template (loader recurses per reference with independent transforms).

Counts:
- per sub-block: IFU 8000, IEX 7400, LSU 7200 std + 2/3/2 SRAM
- per core: 22600 std + 7 SRAM -> 4 cores = 90400 std + 28 SRAM
- uncore: 15000 std in the cross strip + 1500/arm in the band + 8 L2 SRAM
- total ~108k instances; die side solved from cell area so density ~60%

## Placement (non-overlapping by construction)
- std cells are laid into rows with a monotonically advancing cursor
  (`place_std_rows` / `place_std_rows_blocked`), footprint stays w x 1
  (orient N/FN only), so no two cells ever overlap
- SRAM macros sit in dedicated strips/bands (`place_sram_stack` / `place_sram_row`)
- die-side solved: `L = round(sqrt(total_area / 0.60))` so avg density ~60%

## Key rules learned
1. A rotated sub-block keeps a different corner fixed at its placement origin:
   N -> lower-left, W -> lower-right, S -> upper-right, E -> upper-left. Placing
   the origin at the wrong corner makes the rotated core spill into the cross.
2. A block's leaf coordinates are in the block's OWN local frame (origin 0,0);
   the parent places the block at its offset. Do not pre-apply the parent's
   offset inside the child's JSON.
3. Instance name keys that are path prefixes (slash-separated) form tree nodes;
   direct top leaves are folded into the top's aggregate unless given a prefix
   (e.g. `uncore/b_0`, `l2/sram_0`).

## App bug fixed
`vlsi_viewer/physical.py` `global_pt` composed nested block frames outermost-
first, which is wrong for 2+ nesting levels with a rotated parent (the old
sample was only 1 level deep, so it never surfaced). Fixed to apply the frames
innermost-first (`reversed(chain)`). Regression test added:
`tests/test_physical.py::test_nested_rotated_block_two_levels`.
